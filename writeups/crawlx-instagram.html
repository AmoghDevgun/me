How I Beat Instagram's Anti-Scraping Stack

About thirty small things stacked on top of each other — TLS fingerprint, header dance, dynamic referer, cookie set, GraphQL doc IDs, residential proxies. Take any one away and the whole thing falls back to a 10% success rate.

For the last few weeks I've been building crawlX — a service that pulls Instagram profiles, posts, reels and comments at a rate that's actually useful. Anyone who's tried this knows the depressing pattern: the first ten requests work, the next ten get a 401, and by request thirty you're staring at a checkpoint page asking you to log in from a "trusted device." Instagram's anti-bot stack is one of the meanest on the public internet.

This is the story of what broke, what worked, and the parts that took me three rewrites to figure out.

The naive attempt (and why it dies in 30 seconds)

The first thing every tutorial tells you to do is hit https://www.instagram.com/{username}/?__a=1. That endpoint has been dead for years. The slightly less dead one is: 

GET https://www.instagram.com/api/v1/users/web_profile_info/?username={u}

You can curl this from your terminal with a real browser User-Agent. It works… once. Then Instagram fingerprints you and you start getting 401 Unauthorized no matter how perfect your headers look. The User-Agent isn't the problem. The headers aren't the problem. You are the problem. Specifically, your TLS handshake is.

The TLS fingerprint wall

Python's default requests library uses OpenSSL with a cipher suite ordering that no real browser uses. Meta's edge can read your TLS ClientHello — the JA3/JA4 fingerprint — and know within microseconds whether you're a Chrome on Windows or a Python script pretending to be one. No amount of header spoofing fixes this.

The fix is curl_cffi, a Python binding over a patched curl that ships actual Chrome TLS internals: 

from curl_cffi import requests

response = requests.get(
    url,
    headers=headers,
    cookies=COOKIES,
    impersonate="chrome",
    timeout=30,
)

That single impersonate="chrome" argument changed my success rate from "around 10%" to "around 60%." The remaining 40% is everything below.

The header dance

Once the TLS fingerprint is fixed, the headers start mattering again — but not the obvious ones. Instagram's web client sends a handful of internal-looking headers that the server actually checks: 

"x-asbd-id":          "...",   # anti-spam build digest
"x-csrftoken":        "...",   # tied to your cookies
"x-ig-app-id":        "...",   # web app identifier
"x-ig-www-claim":     "...",   # session-bound claim token
"x-web-session-id":   "...",
"x-requested-with":   "XMLHttpRequest",

These aren't documented anywhere. I pulled them out of devtools, then watched which ones the server actually inspected by removing them one at a time and watching what flipped to 401. x-ig-app-id and x-csrftoken are non-negotiable. x-ig-www-claim is the one that quietly burns down your session if it doesn't match your cookies — request looks fine, returns 200, payload is missing the user object.

The Client Hints headers also matter more than I expected:

"sec-ch-ua-full-version-list": '"Not(A:Brand";v="8.0.0.0", "Chromium";v="144.0.7559.133", "Google Chrome";v="144.0.7559.133"',
"sec-ch-ua-platform-version":  '"19.0.0"',
"sec-ch-ua-mobile":            "?0",

If your sec-ch-ua says Chrome 144 but your User-Agent says Chrome 119, Instagram knows. Keep them in sync and bump them together when Chrome ships a new stable.

The dynamic referer trick

Here's the thing that took me embarrassingly long to figure out. When I'd scrape user A, the referer would still be set to user B from the previous call, because I was reusing one big HEADERS dict. Instagram silently degrades responses when the referer doesn't match the resource you're asking for. You don't get an error — you get a thinner payload. The post count drops. The bio links disappear. 

headers = {**HEADERS, "referer": f"https://www.instagram.com/{username}/"}

A per-request shallow copy of the headers with a freshly-stamped referer. Trivial. Took me half a day to notice the payload was wrong.

The endpoint hiding in the APK

The web API is deliberately handicapped — it returns enough to render the site, not enough to actually download what's on it. The mobile client knows more. So I rooted a spare Android, pulled the APK, and went looking for what the web traffic never shows.

What you find through that route is a different surface area: endpoints in the same /api/v1/ namespace whose response shapes carry fields the web client never asks for — direct media URLs for reels being the obvious one. Once you've got the request shape, you can replay it from the scraper with a Chrome-on-Android curl_cffi profile and mobile auth headers instead of the web cookie jar. It's the single biggest payload upgrade in the codebase, and there's no way to find it from web traffic alone.

The three real endpoints

Instagram has three production endpoints I ended up calling, and they each behave differently:

Resource Endpoint Verb
Profile /api/v1/users/web_profile_info/?username=... GET
Posts /graphql/query with doc_id=25345334665119661 POST
Reels /api/v1/clips/user/ POST
Comments /graphql/query with doc_id=25060748103519434 POST

The GraphQL endpoint is where the real meat lives. You don't write a query — you pass a pre-registered doc_id (a persisted query hash) and a variables JSON blob. Those doc IDs change every few months. When the payload suddenly comes back empty, that's the first thing to check.

Comments were extra fun because the GraphQL endpoint takes a numeric media_id, not a shortcode. The conversion is base64-with-a-custom-alphabet: 

ALPHABET = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_"

def shortcode_to_media_id(shortcode: str) -> str:
    media_id = 0
    for c in shortcode:
        media_id = media_id * 64 + ALPHABET.index(c)
    return str(media_id)

Reels were the most annoying — the clips endpoint takes a numeric target_user_id, not a username. So every reel scrape is actually two requests: resolve the username to an ID via the profile endpoint, then page through /clips/user/ with max_id cursors. I cache the username→id mapping for an hour to halve the request count.

Proxies and the bandwidth bill

Residential proxies are non-negotiable — without IP rotation a single host gets soft-banned in about four minutes of sustained scraping. The catch is that they bill by bandwidth, not requests. End-to-end, with the full payload, a profile call comes out to roughly 100 MB per 1000 requests. Worth knowing before you point the scraper at a five-thousand-username list.

Streaming results back

The scraper takes long enough that a synchronous HTTP request is a bad UX. Instead, every scraper endpoint streams NDJSON: 

def _ndjson(obj: dict) -> bytes:
    return (json.dumps(obj, separators=(",", ":")) + "\n").encode("utf-8")

yield _ndjson({"type": "progress", "attempt": attempt, "status": "fetching"})
...
yield _ndjson({"type": "post", "data": post})
...
yield _ndjson({"type": "complete", "scraped": yielded})

The frontend gets progress events as each page is fetched, individual posts/reels as they're extracted, and a final complete message. The backend doesn't have to buffer a 5MB response — it pipes it straight through.

What I'd do differently

A few things I'd skip if I were starting over:

  • Don't bother with requests + a custom adapter. Just use curl_cffi from day one. Every hour spent fighting OpenSSL cipher ordering is an hour you could have spent on actual logic.
  • Build the traffic counter on day one, not day fifteen. You will be wrong about how much bandwidth you're using, by an order of magnitude, in both directions.
  • Cache the username → user ID resolution. It's a free 50% reduction in profile-endpoint hits for any flow that touches reels.
  • Watch the payload shape, not just the status code. A 200 that quietly drops fields is the worst possible failure mode and it's how Instagram tells you "we noticed."

Closing

Bypassing Instagram isn't one trick. It's about thirty small things stacked on top of each other — the TLS fingerprint, the cookie set, the dynamic referer, the GraphQL doc IDs, the per-endpoint pagination, the retry-but-not-on-401 policy, the residential proxy, the streaming protocol, the traffic accounting. Take any one of them out and the whole thing falls back to a 10% success rate.

The lesson I keep relearning: the public web isn't really public. It's a permission system that happens to be enforced by HTTP. Once you start seeing it that way, scraping stops feeling like coding and starts feeling like protocol archaeology. Which is, honestly, the fun part.
