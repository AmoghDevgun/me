Reverse Engineering · Vercel BotID

From Deobfuscation to a Live BotID Bypass

A great writeup helped me understand Vercel's c.js challenge. However, actually replaying a passing request from a script (which required handling TLS fingerprints, an AST interpreter, and more) was a completely different problem.

A while back, I read an excellent writeup on reverse engineering Vercel's BotID challenge. It walked through the structure of c.js, the string-array obfuscator, the X(...) function, and how the browser signal payload is shaped. I learned a lot from it, but it stopped at the understanding phase. It explained what the challenge does, but not what it actually takes to replay a passing request from a script.

This post is the next step. I built a small CLI that takes a fresh c.js URL, deobfuscates it, extracts the live crypto material out of the script, forges the encrypted fingerprint, and POSTs to a BotID-protected endpoint while the server returns {"isHuman":true,"isBot":false}. Everything below is what I actually had to figure out to get that to work.

In the vercel-botid/ repository, run_flow.mjs acts as the orchestrator while the rest of the files are pieces it pulls in.

The flow at 30,000 feet

c.js URL
  │
  ▼
[impersonated Chrome fetch]   ← curl_cffi via a python subprocess
  │
  ▼  raw obfuscated source
[analyze.js]                  ← deobfuscator (string-array + CF flattening)
  │
  ▼  output.js (readable)
[extract_gz_ast.mjs]          ← mini AST interpreter pulls k, a, S out
  │
  ▼  G = k+a (PBKDF2 password), S (marker), Z (auto fingerprint)
[encryptLikeD]                ← PBKDF2(SHA-256, 100k) + AES-GCM
  │
  ▼  s = base64(salt | iv | ciphertext)
[extract tail X(...) args]    ← b, v, e (JWT-ish), d, vr
  │
  ▼  { b, v, e, s, d, vr }
[post_contact_test.mjs]       ← POST with x-is-human header
  │
  ▼
{"isHuman":true,"isBot":false,"isVerifiedBot":false,"bypassed":false}

Each box is a thing the original writeup either glossed over or didn't touch. Worth unpacking the interesting ones.

TLS fingerprinting is the first wall

This was the first big surprise. When I first ran my deobfuscation tool against a freshly-fetched c.js, my locally generated payload was perfect (it had the same shape, same encryption, and same X call), yet the server still rejected it. After a lot of staring, I realized that the request fetching c.js never properly made it past the edge. Or rather, it made it past, but the response I received was a slightly different script tailored to a "suspect" client. This meant my extracted k, a, and S variables were already poisoned before the deobfuscation even started.

Node's fetch advertises a Node TLS handshake. Even with a perfect Chrome user agent string, the JA3/JA4 fingerprint is wrong, and Vercel's edge network knows it. The fix was to wrap curl_cffi in a Python subprocess and call it from Node. The curl_cffi library ships with bundled BoringSSL builds that perfectly replay real Chrome handshakes, including cipher order, ALPN, extensions, and X25519MLKEM768.

The Node side is in curl_impersonate.mjs. It JSON-encodes a request to stdin of a Python helper, the helper does the actual HTTP work, and prints {statusCode, body, url} back on stdout: 

// vercel-botid/curl_impersonate.mjs
output = execFileSync("python3", [pythonHelperPath], {
  input: JSON.stringify({
    url, method, headers, body,
    impersonate: chrome.profile,   // e.g. "chrome142"
    ...
  }),
  encoding: "utf8",
});
# vercel-botid/curl_cffi_request.py
from curl_cffi import requests
response = requests.request(
    method, url,
    headers=headers, data=body,
    impersonate=impersonate,
    default_headers=False,   # critical: don't let curl_cffi add its own UA/Accept
    ...
)

Two non-obvious things here:

  1. default_headers=False. Without this, curl_cffi quietly adds its own User-Agent, Accept, Accept-Encoding etc. on top of whatever you passed. Now you have two User-Agent headers (or one wrong one) and the fingerprint is off again. Turning defaults off lets the Node side dictate every byte of the header block.
  2. The Chrome profile string has to be live. I used chrome142 because that matched the version string in my User-Agent. If you mismatch the profile and the UA (for example, chrome142 with a UA claiming 131), the edge network gets suspicious since the HTTP/2 SETTINGS frames and the UA tell different stories.

The headers sent by the orchestrator when fetching c.js are documented in run_flow.mjs. They are a faithful copy of what a real Chrome browser sends for a top-level navigation: sec-fetch-site: none, sec-fetch-mode: navigate, priority: u=0, i, the whole suite. Anything missing is a fingerprint.

Deobfuscation: just enough to keep moving

The original writeup explains the obfuscator beautifully so I won't re-tread it. The short version: there's a function that returns a giant string array, a self-shuffling IIFE that rotates the array a deterministic number of times, and a decoder that takes (0x<index>, <salt>) and returns the real string.

My analyze.js script does essentially the standard process: it finds the three pieces by structural signatures (array literal of all strings, while-loop IIFE, decoder calling the array function), evaluates them in a fresh vm context to get a working decodeString, and then walks the AST replacing every (0x###, "salt") call site with its string literal. After that, it runs three folding passes for string concatenation, a numeric evaluate() pass using Babel's built-in features, and a control-flow-flattening resolver. This resolver hunts down the large proxy object (which has over 15 properties including strings, numbers, binary operation wrappers, and call wrappers) and simply inlines every reference to it.

The one part worth highlighting is the CF-flattening resolver, because it's the difference between "deobfuscated" and "actually readable". The proxy object looks roughly like: 

var Q = {
  aB: "some-string",
  cD: 0x42,
  eF: function (a, b) { return a + b; },      // binary wrapper
  gH: function (f, x, y) { return f(x, y); }, // call wrapper
  ...
};

Until you replace Q.eF(a, b) with a + b and Q.gH(f, x, y) with f(x, y) everywhere, the script reads like a state machine. After you do, the entire X(...) payload-builder becomes obvious. My resolver classifies each property by its body shape and inlines call sites accordingly, as seen in analyze.js:175.

After all this, the output.js file becomes something a human can actually read. But I didn't need a human to read it; I needed a program to read it, which led to the next problem.

A tiny AST interpreter to pull crypto material out

The challenge derives an encryption password at runtime by concatenating two values: call them k and a. Both get assigned inside the deobfuscated script, but their right-hand sides are non-trivial expressions involving btoa, String, member access on a var I = {...} constants object, sometimes a String.fromCharCode chain. Statically computable, but Node can't eval them safely (they're embedded inside a larger script that does things you don't want to run).

Because of this, extract_gz_ast.mjs includes a minimal Babel-AST evaluator. It's about 100 lines of code for the evaluate(node, env) function, and it supports exactly the node types these expressions use: literals, identifiers from a known environment, unary/binary/logical ops, conditionals, member access, object/array expressions, and call expressions where the callee resolves to a function in the environment. Everything else throws an error.

The env it runs in is hand-built: just String, a polyfilled btoa, and whatever it can extract from the var I = {...} constants object in the same scope: 

// vercel-botid/extract_gz_ast.mjs:337
function createEnvFromI(scopePath) {
  const env = new Map();
  env.set("String", String);
  env.set("btoa", makeBtoa());

  const iBinding = scopePath.scope.getBinding("I");
  if (!iBinding?.path.isVariableDeclarator()) return env;
  if (!t.isObjectExpression(iBinding.path.node.init)) return env;

  env.set("I", evaluate(iBinding.path.node.init, env));
  return env;
}

Then, for each target variable (k, a, and the S property on the fingerprint object), I walk the AST looking for the assignment, evaluate the right-hand side in that environment, and stash the value. There's a small heuristic to prefer assignments that reference I since those are the actual values after deobfuscation, rather than earlier dead-store assignments. For S specifically, I prefer the property when it sits inside an object literal that has the full {p, w, s, h, b, d} shape. This ensures we are getting the actual fingerprint object and not a decoy.

The output: G = k + a (the PBKDF2 password), and S (the marker that the server stamps the request with). Both are required and both change every time the server serves a fresh c.js.

Re-implementing the encryption

The fingerprint object Z (browser signals: {p, S, w, s, h, b, d}) gets JSON-stringified, then encrypted in the browser using a routine that, after deobfuscation, is unambiguously WebCrypto's PBKDF2 + AES-GCM. Salt 16 bytes, IV 12 bytes, 100k iterations, SHA-256, AES-256-GCM, base64 of salt | iv | ciphertext+tag.

Once you have G (password) and Z (payload), reimplementing this in Node is a 40-line function (run_flow.mjs:208): 

const keyMaterial = await webcrypto.subtle.importKey(
  "raw", enc.encode(password), "PBKDF2", false, ["deriveBits","deriveKey"]
);
const key = await webcrypto.subtle.deriveKey(
  { name: "PBKDF2", salt, iterations: 100000, hash: "SHA-256" },
  keyMaterial,
  { name: "AES-GCM", length: 256 },
  false, ["encrypt"]
);
const cipherBuffer = await webcrypto.subtle.encrypt(
  { name: "AES-GCM", iv }, key, enc.encode(JSON.stringify(payload))
);
// combined = salt || iv || cipherBytes; return base64(combined)

The thing that took me by surprise is that there is no MAC outside of the AES-GCM tag. Once you have G, you are completely done. There is no separate HMAC envelope and no separate signature on the payload. The integrity purely relies on knowing the password derived from k+a, which implies you successfully ran the script they served you. This is exactly why fetching c.js with the wrong TLS fingerprint matters so much: if the server gave you a different k/a, your derived key is wrong and decryption on the server fails.

The Z builder is located in run_flow.mjs:125. It defaults everything to false (meaning no leaks detected, no headless flag, and no automation hints) and pulls a (vendor, renderer) tuple from a webgl.json GPU fingerprint pool. It uses a random selection because different machines have different GPUs, making a varying w field realistic. Finally, the s slot (the PBKDF2 marker) gets stamped with the S value we pulled out of the script.

The tail X(...) call

The challenge ends with a single call that takes five positional arguments. Three of them (b, v, and vr) are constants baked into this particular c.js script. One (e) is an eyJ-prefixed string, which looks like a JWT-shaped token and is also baked in for this challenge. The last one (d) is a constant the server uses to keep state. These are the values the server expects to see echoed back in the x-is-human header so it can correlate the request to the challenge it issued.

Rather than try to interpret this call, I just find it: walk the AST for any CallExpression with exactly five literal-ish arguments where arg[2] is a number, arg[3] is a string starting with eyJ, and arg[4] is a string (run_flow.mjs:92). One match per script. Pull those five values out, drop the s we just computed in for the encrypted slot, and JSON-encode the result.

That JSON is the x-is-human token.

Sending the request

The post_contact_test.mjs script is the smallest piece. It takes a URL, a body, and the x-is-human token (from arguments or piped via standard input) and sends a POST request through the same curl_cffi impersonator. The header set matters just as much as it did for fetching c.js, but now it's a CORS XHR and not a navigation: sec-fetch-site: same-origin, sec-fetch-mode: cors, sec-fetch-dest: empty, accept: */*, priority: u=1, i. Plus three Vercel-specific headers the BotID client SDK adds in real browsers: x-is-human (the token), x-path (the destination pathname), x-method (the actual method).

When everything lines up, the BotID-protected endpoint returns:

{"isHuman":true,"isBot":false,"isVerifiedBot":false,"bypassed":false}

Seeing bypassed: false is the real prize. It means we didn't just use a developer escape hatch like the x-botid-bypass header. Instead, the server actually ran our payload through its detection and confidently concluded we were a human using a real Chrome browser.

What I'd do differently

A few notes for anyone walking this road:

  • Don't try to fetch c.js from Node fetch or stock curl. You'll waste hours debugging deobfuscation that's perfectly correct against a script the server poisoned. Get the network layer right first.
  • The CF-flattening proxy is the gatekeeper to readability. If you skip it, you'll think you need to interpret a state machine to find k and a. Once it's inlined, the assignments are right there.
  • Keep an AST evaluator instead of running the deobfuscated code. It's tempting to vm.runInNewContext(output.js) and pluck the values out of the resulting context. Don't. The script does network I/O, touches window, sets timers, and is generally hostile. A 100-line interpreter that only handles what the constant expressions need is safer and faster.
  • The webgl.json fingerprint pool needs to be real. Hand-rolled (vendor, renderer) tuples that don't correspond to a shipped GPU/driver combo are an obvious tell. I scraped a public dataset of real WebGL fingerprints and normalized to {v, r}.

The original writeup was the map, and this project was the actual trip. Both parts are necessary since you can't write the second without first reading something like the first. However, bridging the gap between "I understand what the script does" and "I can replay a successful request whenever I want" turned out to be the majority of the work.
